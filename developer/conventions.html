Conventions and Testing¶

Code style¶

  • Two-space indentation; camelCase for methods, functions and variables, CapWords for classes, UPPER_CASE for constants. (The commands are the exception: new_node and the like, because their names are the command-line words.)

  • Type hints throughout, checked with mypy; @override on overriding methods. From the project directory:

    MYPYPATH=../pythonUtils/src python3.14 -m mypy src/sn

    Keep sn’s own modules free of errors (those it reports in pythonUtils’ modules are that project’s). Where a check can’t be satisfied, a # type: ignore[code] names the error it ignores.

  • A leading underscore marks what’s private to a class or module – and, on a context, keeps a method from becoming a command.

  • Imports that would be circular (eg: the view classes, from each other) are made inside the functions that need them.

Docstrings¶

Docstrings are reStructuredText, and are the API reference (see Overview), so every module, class and public function has one – at least a line saying what it does or gives. They say what something is for and why it is the way it is; the parameters are given in Sphinx’s field lists:

def gap(snap:Snapshot, i:int, j:int, *, fast:bool=False) -> tuple[float, float, float]:
  '''
  The gap between two objects' edges ...

  :param snap: The layout's snapshot.
  :param i: An object's index in *snap*.
  :returns: ...
  '''

The types are the annotations’ – the API reference shows them with each parameter and the return value (autodoc_typehints = "description" in conf.py) – so a docstring doesn’t repeat them: no :type x: or :rtype: that says what the signature says. A field is there for what it adds:

  • :param x: says what x is for (not just that it’s there: fast, above, needs no field);

  • :returns: says what’s returned (an empty one says nothing);

  • :type x: or :rtype: only to say more than the annotation does (eg: for a parameter that has none, or is annotated Any).

A method marked @override that has nothing to add to what it overrides has no docstring: the API reference shows the overridden method’s.

Names of other things are in italics (eg: SNGView.shouldHide()), or cross-referenced (:py:meth:`...`) where the link is worth having. A constant or attribute is documented by a string just after it.

Changes go through commands¶

Anything that changes a model or a view, and that the user can do, is a command on a context (see Architecture), not a direct call – so it can be undone, and typed. Several steps that make one user action are grouped in a CompositeCommandMgr, so they’re undone together. Code that only computes or displays (eg: a query, a report) needn’t be a command.

Tests¶

The tests are in test/, one package per layer (test_model, test_controller, test_view, …), written with unittest. Run them with Python 3.14, with src and ../pythonUtils/src on the path, and SN_NO_SAVE_PROMPT set so nothing asks to save at exit. Eg, from the project directory:

SN_NO_SAVE_PROMPT=1 PYTHONPATH=src:../pythonUtils/src python3.14 -m unittest discover -s test

test/test_model/test_reasoner.py is the reasoner’s specification: any reasoner engine must pass it (see The Reasoner). test_rules.py covers rules and definitions (symmetry, transitivity, attributes, isa conclusions, new objects, and examples such as brother, bachelor and grandparent).

Tests that save models must save them somewhere of their own: build the model under a fresh temporary directory, and check its URL is there before calling save() – never save to a path that could be a real file.

The documentation’s examples¶

The User Guide’s screenshots, the example models, and the Developer Guide’s example program are made or checked by the scripts in tools/docExamples/ (see Overview). When a change alters what they show, rerun them – makeExamples.py, showScene.py <scene> --capture sphinx/source/images/user, checkPetsapp.py – rather than editing the pictures or the guide’s code by hand.
