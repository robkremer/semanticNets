The Model¶

The model package, sn.model, is the data and its meaning. It has no user interface, and can be used (and is tested) on its own.

Objects¶

GraphObject

Anything in a model. It’s a type or an individual (isIndividual()), has a name, and has attributes (below). Its types – its parents – are given by its outgoing isa relations (getParents()), and isa() answers whether it’s of a type, directly or not.

Node

A node.

Relation

A relation: a GraphObject with a source and a destination, so relations can relate relations. A relation’s ends may be set locally (localSrc) or inherited from its type (src, dst); for a relation type, the ends are its signature (domain, range).

IsaIndividual

An isa link. These are relations like any other – so they can be drawn, selected and deleted – and are what makes an object’s types.

Collection

A node with members (not currently offered in the GUI).

The graph structure (objects, incoming and outgoing relations) comes from pythonUtils’ util.abstractGraph.

Models¶

A Model holds GraphObjects, and is saved in a file. A model builds on other models – its super-models, at least the system model – and can use their objects (as types, or as ends of relations); a reference to another model’s object carries that model’s URL.

The system model, TopModel (sn:/sn), is made in memory at start-up and is write-locked. sn: URLs are names of models in memory, not files: the base rules, read from a temporary copy of a file that comes with the program, are sn:/baseRules, and models refer to both by these names (see PRDb.namedURLs; the old names, eg: sn:/sn.xml, are read as aliases: see PRDb.aliases). Attributes¶

Objects have attributes through SNAttributedObject, built on pythonUtils’ util.attribute. An attribute has a type and a value, and a Restriction on how it’s inherited (eg: NOINHERIT: subtypes and instances must fill it in themselves; NOOVERRIDE: they may not change it). An object’s effective value of an attribute is its own, or the one it inherits down its isa links.

Attributes are used for:

  • the object’s own data (name, note, anything the user adds);

  • the relational properties, as boolean tags on relation types (symmetric, transitive, …), which are deliberately not inherited;

  • a variable’s constraints (below);

  • how it’s drawn: the vis/ attributes, read by the view (see The Graphical View). These are inherited, so a type sets them for its instances.

Patterns: variables, contexts and constraints¶

An object whose name starts with ? is a variable. A relation contained by a context (the destination of a relation that isa contains: eg: antecedent) is part of a pattern, as is any relation with a variable at either end. isPatternElement() says whether an object is part of a pattern; if so, it describes the pattern, not the world, so the reasoner doesn’t take it as a fact, and getRelatedTo() and the like leave it out.

A variable’s constraints are the text of its constraints attribute (eg: alive, age: 30, owner: ?o). sn.model.constraints parses it (parseConstraints()), formats it back (formatConstraints()), splits it from a name typed with :where: (splitWhere()) and merges edits into it (mergeConstraints()). A text attribute – rather than, say, one attribute per constraint – keeps the constraints in one place to edit, and away from the variable’s own attributes (a variable ?p with a constraint age: 30 doesn’t have an age; it matches things that do). Older models, which stored constraints as attributes of their own, are converted when they’re read (migrateConstraints(), via Model._migrate).

Copying¶

Cut, copy and paste work on the model (sn.model.copying): a view can’t show an object twice, so a copy has to be new model objects. copyObjects() takes a snapshot – a Clip – of the objects, the contents of any contexts among them, and their isa links; pasteInto() makes new objects from it, with new ids. What isn’t copied (a type, a relation’s end) is referred to, not copied, so a clip can be pasted only into a model that can see those objects: the one it came from, or one that builds on it (pasteProblem()). The commands are copy, cut and paste on the ModelContext; a view adds to the clip how it showed the objects (Clip.geometry), so it can show the copies the same way (SNGView.showPasted()).

Persistence¶

Models (and views) are PRDbs: databases of PRObjects, each with an id, saved to and read from a URL. pythonUtils does the work; what a class provides is a description of how to rebuild an object – its getInstantiationInfo() – in terms of:

  • constructor arguments (conArgs, conKWArgs): what’s passed to the class to make the object;

  • post-construction setters (postconSetters): properties set once it’s made (eg: a view’s hidden categories, or its animation settings);

  • final setters (finalSetters): run once everything in the file has been read – when the objects it refers to exist (eg: Model._migrate).

Each is a ParamInfo or PropertyInfo, with a getter and setter, so a class can save what it likes in whatever form suits it. References between objects are saved as PReferences and resolved lazily.

The file format is chosen by a SerializationStrategy. The default is XML3 (util.persistence.serializeXML3), a compact XML: simple values and references are written as XML attributes rather than as elements of their own. Each file is a head, then the model or view: the head says what it is, its URL, its model (a view’s) or super-models (a model’s), how many objects are in it, and the versions of the format, of the program, and of the structures it’s saved in (sn.SCHEMA_VERSION: change it when they change). The head can be read without the rest (eg: by the model directory: see sn.model.directory). Files are read by trying the strategies in turn – those that recognise the file’s start, the preferred ones, and those for the file’s extension, first – so the older formats are still read.

Copied and moved files¶

References to other files are written relative to the file being written, when the target is close by (in the same folder, below it, or at most PRDb.MAX_UP folders up): a folder of models and views can then be moved or copied as a block. Each file’s head records the URL it was saved to, and the one before that. When a file is read from somewhere else (readFile()), it’s noticed and reported, and a relative reference that isn’t found next to the copy is looked for where the original was.
