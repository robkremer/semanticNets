sn.model.reasoner module¶

The engine-independent interface to back-end reasoners for Model objects.

A reasoner engine subclasses Reasoner (see sn.model.clingoReasoner.ClingoReasoner). What is shared here:

  • Reasoner.facts() exports the model as engine-neutral facts. Their vocabulary is the contract every engine reasons over:

    obj(O)

    every GraphObject (including those of super-models)

    individual(O)

    GraphObject.isIndividual()

    kind(O,K)

    K in top, node, relation, isa

    collection(O)

    O is a Collection (also of kind node)

    name(O,S)

    GraphObject.name

    const(K,O)

    well-known objects: top, relation, isa, node, …

    parent(X,P)

    GraphObject.getParents() (incl. implicit defaults)

    lsrc(R,C), ldst

    locally set relation endpoints (Relation.localSrc/.localDst)

    domain(T,C), range

    the signature of relation type T (Relation.domain/.range)

    src(R,S), dst

    effective endpoints (Relation.src/.dst, inherited)

    link(R,S,D)

    individual, non-isa relation R with both endpoints

    prop(T,P)

    relation type T is tagged with P (reflexive, irreflexive, symmetric, asymmetric, transitive)

    member(C,M)

    Collection membership

    attr(O,K,V)

    effective non-“vis/” scalar attributes

    lattr(O,K)

    O has attribute K locally

    card(T,Dir,Min,Max)

    relation type T’s cardinality: each source (Dir out) or destination (in) has Min..Max others by T (Max -1: any number). See CARDINALITY.

    card_error(T,K,M)

    T’s cardinality attribute K can’t be read: message M

    pattern(X)

    X describes a pattern (in a rule etc.), not the world (see GraphObject.isPatternElement())

    var_kind(X,K)

    X is a variable over K: individual, type or any (see GraphObject.variableKind() and sn.model.names)

  • Inferences and Violation are what every engine returns, and the violation codes (see _MESSAGES) are shared.

  • The typed queries (Reasoner.related(), Reasoner.isa(), …) work with any engine. Reasoner.query() is the engine’s native query language (see Reasoner.language), and so is not portable.

The semantics every engine must implement are pinned down by test/test_model/test_reasoner.py: an engine is conforming if it passes ReasonerSpec.

The Model remains the single source of truth: reasoners never modify it.

sn.model.reasoner.CARDINALITY = {'cardinality': 'out', 'inverseCardinality': 'in'}¶

The cardinality attributes of a relation type – like the relational properties, its own (not inherited by its subtypes): how many objects each source is related to by it (or by its subtypes: a father is a parent), and how many each destination is related from. Eg: has-father’s “cardinality” “1..1” (everyone has exactly one father), has-parent’s “2..2”, has-child’s “0..*”, a desk’s has-desk “inverseCardinality” “0..1” (no desk is two people’s). See parseCardinality() for how they’re written, and clingoReasoner.lp for what they mean: too many different (named) objects is an error and too few (for the domain’s individuals: the range’s, for “in”) a warning; at most one makes the objects the rules invent the same object (as each other, or as a named one); and exactly one invents one where the model has none.

sn.model.reasoner.patternOf(context, parts=None, outer=None)¶
Parameters:

  • parts (tuple[GraphObject, ...] | None) – The “contains”-family relation types to read the pattern from. By default, all of them other than “consequent”, “definiendum” and “required”: so for a rule, its antecedent, for a definition, its definiens, and for a requirement, its condition.

  • outer (Pattern | None) – The pattern this one’s evaluated within, if any (eg: a requirement’s condition, for its required part): its value variables have values here too.

  • context (GraphObject)

Returns:

The Pattern of context: everything it contains (through parts).

  • A contained relation must hold, between its (local) ends, for each of its types; an end it doesn’t have is “something”.

  • A contained isa link is a type constraint; so are a variable’s own isa parents (other than the base node/relation types, which say nothing).

  • A relation whose type is a variable ranges over relation types.

  • A contained “distinct” relation says its two ends are different objects (the usual “for all x, y: x != y, …”), rather than a relation to find.

  • A variable’s own attributes are constraints on what it matches (see GraphObject.constraints()).

Return type:

Pattern

sn.model.reasoner.ruleOf(rule)¶
Parameters:

rule (GraphObject)

Returns:

The RuleSpec of rule: its antecedent is patternOf(rule); its consequent is what it contains through “consequent” relations:

  • A relation concludes a relation, between its (local) ends, for each of its types – which may be variables.

  • A variable’s constraints (see GraphObject.constraints()) are conclusions if it’s the consequent’s own variable (not one of the antecedent’s nodes, whose constraints are tests).

  • An isa link concludes an isa link.

  • A consequent variable the antecedent doesn’t bind (by name) stands for a new object, one per match: it’s concluded to exist, isa its types (as drawn), and have its constraints. (Relation types can’t be new.)

  • Value variables (“?a”) must be bound by the antecedent.

  • ”distinct”, and relations or isa links with a missing end, aren’t supported: they’re reported as problems, and the rule isn’t used.

The two rules a definition amounts to: its definiens (the meaning) implies its definiendum (the term defined), and its definiendum implies its definiens – each part of it. _finish(ret)¶

What every engine does with its results, before returning them from run():

  • A violation is reported once per set of objects it’s about: eg: an asymmetric relation between a and b once, not again for b and a. (Of such, the one whose args come first in the models’ order is kept.)

  • A constraint’s violations get its message (see ConstraintSpec).

  • Objects that must be the same (Inferences.same) are merged (see mergeSame()).

  • The relation triples (holds, …) are put in the models’ order.

  • Unless showSysRules, the base rules’ conclusions aren’t reported as rule conclusions (fired, …): what they conclude is in holds, inferred, … as any inference is.
