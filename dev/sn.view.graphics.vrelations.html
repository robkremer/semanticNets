This class has to take special measures to avoid an address fault because Relations may reference other relations, so there is no way to ensure that toNode and fromNode idString-to-addresses have already be registered. To get around that, if there had been an address fault in self.getArgs(), it will have put the str isString in place of the pointer. The pointer(s) will be properly instantiated (etc) on a second pass when the owner container calls the self._post__init__() method.

_resolveEnd(end)¶

The view object end (“src” or “dst”) of this relation should be drawn to, recording whether it’s inherited (see self.inheritedEnds):

  • the relation’s own (local) endpoint, if it has one;

  • otherwise the one it inherits from its type (drawn faded – see _styleEnds());

  • or None – a dangling end – if there’s none, or it would be top: a line to top says nothing, and would drag top into the view. (A relation whose own end is top – eg: the relation and isa types – is drawn to top if top is already shown, but never adds it.)

reposition(aggressive=False, suppressDraw=False, adjustPos=True, place=False)¶
Parameters:

  • adjustPos (bool) – [default=True] When True (the normal case, e.g. called once at the end of a drag), a relation that isn’t centred between its src/dst also gets a full self.adjustPos() call, which may invoke the local layout heuristic (FindFree) to resolve overlaps. When False (passed down from a live drag via notifyNodeMove()), the relation still repositions/redraws to track its connected nodes’ current positions, but skips that extra layout-heuristic call, so a relation doesn’t jump to a FindFree-computed spot on every single mouse-motion tick while something it’s connected to is being dragged.

  • place (bool) – [default=False] Put it between its ends even if it doesn’t float (eg: a new relation type, once: see floating()).

  • aggressive (bool)

  • suppressDraw (bool)

PANE_MARGIN = 6.0¶

How far in from its pane’s edges a contained relation’s floating label is kept (see placedLabel()).

placedLabel(x, y)¶

Where a floating label centred on (x, y) goes: there, unless that’s out of place –

  • if the relation is contained by a context (see SNGView.containmentHomes()), moved the least it takes to put it in the pane it belongs in (antecedent, consequent, …), so it doesn’t float out of its window, or into the other pane, when its ends are far apart;

  • and moved out of any window it doesn’t belong in (see SNGView.belongsIn(): eg: a relation between something in a rule and something outside it, whose ends’ midpoint is in the rule’s window).

gapMidpoint(a, b)¶

Where a floating label between a and b goes: midway along the visible part of the line between their centres – from where it leaves a’s edge to where it meets b’s – so a big shape (eg: a context window) doesn’t swallow the label of a relation to something close by. If they overlap (either’s centre is inside the other), or it’s a self-loop, midway between the centres.

chooseNewEndpoint(end)¶

Let the user pick a new end (“src” or “dst”) for this relation with an elastic line, then change it in the model (as one undoable command).

Any object may be chosen – relations connect nodes and relations in any combination (eg: a rule’s antecedent can contain a relation) – except that an isa link must connect two nodes or two relations, its new parent (dst) must be a type, since individuals can’t have children, and it mustn’t make an isa cycle (eg: a type its own type). Dropping the line on empty space clears the end instead (the relation then inherits its type’s), except for an isa link, which needs both ends.

Parameters:

end (str)

Return type:

None
