sn.view.graphics.connectors module¶

Draws a source/label/destination connector: two lines (source-to-label, label-to-destination) that terminate at the edges of their respective VObjects and, together, trace a single smooth curve from the center of source’s bounding box through the center of label’s, to the center of destination’s. source and/or destination may be None – see drawSmoothConnector()’s docstring for how a missing endpoint degrades the shape (a single straight segment to whichever is present, or a no-op if neither is).

Deliberately kept as free functions rather than methods on any class (a Strategy/”behaviour” pattern): drawSmoothConnector() and drawStraightConnector() below share an identical signature, so calling code can hold a function pointer and swap implementations — e.g. the straight variant during animation, the smooth one for a settled layout — without knowing which one it’s using. Add further variants the same way.

Redraws update canvas items IN PLACE rather than delete-and-recreate: pass the ConnectorIDs a previous call returned back in via ids and each item that already exists gets coords()/itemconfigure()’d rather than replaced — no leaked duplicates if a caller refreshes every animation frame, no z-order reset, and colours/arrowheads/diameters are picked up fresh from every call (nothing is assumed to stay fixed after the first draw). Pass ids=None (or omit it) to draw fresh items; ConnectorIDs.deleteAll() is there for when the connector itself is going away for good.

sn.view.graphics.connectors._SELF_LOOP_GAP: float = 3.0¶

Target visual gap (in view units) between the two lines of a self-loop connector (see _selfLoopOffset()) – deliberately a rough constant (“about 3 units”, per Rob) rather than anything derived, so it’s the one knob to turn if the drawn separation looks too tight or too wide.

sn.view.graphics.connectors._selfLoopOffset(cs, cl, lineWidth)¶

The offset to push source’s and destination’s shared center apart by when source is destination (a self-loop) – see the “source is destination” handling in drawSmoothConnector()/drawStraightConnector().

Without this, source’s and destination’s centers (and therefore every point derived from them) are identical, so the source→label and label→destination lines retrace exactly the same path instead of forming a visible loop. Add the returned offset to cs for the source side and subtract it for the destination side (or vice versa – only the fact that they’re opposite matters) before doing anything else with those points, so every downstream boundary-clip/curve calculation sees two distinct “centers” a small distance apart instead of one.

Offsetting along a true perpendicular to the source/dest→label line would need a normalize + rotate-90° (a sqrt and a couple of multiplies) for every self-loop redraw. Since this only needs to look reasonable, not be exact, picking a single axis – y for a line closer to horizontal, x for one closer to vertical – gets a visually-parallel-enough offset for a couple of comparisons instead, which matters here since redraws can happen every frame of a drag/animation (see drawStraightConnector()’s docstring).

Parameters:

  • cs (tuple[float | int, float | int]) – source’s (== destination’s) true center point.

  • cl (tuple[float | int, float | int]) – label’s center point – only its direction from cs matters, to decide which axis to offset along.

  • lineWidth (float) – The line’s stroke width (create_line()’s “width” option, or its default of 1 if not given), so thicker lines still end up visibly separated rather than just touching edge-to-edge.

Returns:

An (x, y) offset with exactly one non-zero component, sized so that adding it to one side and subtracting it from the other leaves about _SELF_LOOP_GAP view units of daylight between the two lines.

Return type:

tuple[float | int, float | int]

sn.view.graphics.connectors._bezierBlossom(p0, p1, p2, ta, tb)¶

The middle control point of the EXACT quadratic-Bezier sub-arc spanning parameters [ta, tb] of the curve [p0, p1, p2] — i.e. Q1 such that [_bezierPoint(p0,p1,p2,ta), Q1, _bezierPoint(p0,p1,p2,tb)] is a quadratic Bezier tracing precisely that portion of the original curve (not an approximation). sn.view.graphics.connectors._findBoundaryParam(vobj, p0, p1, p2, tInside, tOutside, iterations=24)¶

Bisect the Bezier’s parameter t between a point known to be inside vobj (tInside) and one known to be outside it (tOutside) to find where the curve [p0,p1,p2] crosses vobj’s boundary — the curved-path analogue of VRelation.findIntersection()’s straight-line bisection, but operating directly on the curve’s parameter instead of on a straight line between two points, so the result is an exact point ON the curve rather than a straight-line approximation.

24 iterations halves the search interval 24 times (~1 part in 16 million of the full curve) — comfortably sub-pixel for any on-screen curve length, so a fixed count is used rather than a pixel-distance stopping condition.

Parameters:

  • vobj (VObject | Callable[[tuple[float | int, float | int]], bool]) – The shape being clipped against (needs .containsPt()) – or what tests whether a point’s in it (see _insideTest()).

  • tInside (float) – A parameter value where _bezierPoint(…) is inside vobj.

  • tOutside (float) – A parameter value where _bezierPoint(…) is outside vobj.

  • p0 (tuple[float | int, float | int])

  • p1 (tuple[float | int, float | int])

  • p2 (tuple[float | int, float | int])

  • iterations (int)

Return type:

float

sn.view.graphics.connectors._clippedArc(vobj0, vobj2, p0, p1, p2, granularity=1)¶

Clip the quadratic Bezier [p0,p1,p2] (p0 == vobj0.centerPt(), p2 == vobj2.centerPt()) to the portion that lies between vobj0’s and vobj2’s boundaries, returning the exact sub-arc’s own [Q0, Q1, Q2] control points (via _bezierBlossom) — ready to hand straight to a 3-point smooth Tk line.

sn.view.graphics.connectors._upsertLine(canvas, existingID, coords, tags, opts)¶

Create a line item, or update one in place if existingID is still a live “line” item — coords() to move/reshape it, itemconfigure() to apply every option in opts fresh (fill, width, arrow, arrowshape, smooth, dash, …), so nothing from a prior draw silently survives a redraw where the caller changed it. If existingID is set but isn’t a line any more (or doesn’t exist), it’s deleted first and a fresh item is created — should not normally happen, but is handled rather than raising.

coords() and itemconfigure(smooth=…) both correctly handle the item’s point count changing between calls (verified empirically), so this also works when existingID is being handed between drawSmoothConnector’s 3-point arcs and drawStraightConnector’s 2-point segments.

Parameters:

  • canvas (Canvas) – The canvas the item lives (or will be created) on.

  • existingID (int | None) – A previous call’s item id for this line, or None to always create a new item.

  • coords (Sequence[float]) – Coordinate sequence for canvas.coords()/create_line().

  • tags (Sequence[str]) – Canvas tags to (re)apply.

  • opts (dict) – create_line()/itemconfigure() keyword options — fill, width, arrow, arrowshape, smooth, dash, etc. — re-specified in full every call.

Return type:

int

sn.view.graphics.connectors._drawSingleSegment(label, other, otherIsSource, terminators, prior, lineColor, fillColor, tagList, lineOpts)¶

Draw (or update) the one straight segment from label to other, with its terminators, for when the connector’s other endpoint (source or destination) is missing entirely.

With only two points there’s nothing left to curve, so this single- segment case is the same regardless of whether the caller wanted drawSmoothConnector() or drawStraightConnector() — both delegate here for it rather than duplicating the clip/line/terminator logic.

The OTHER side of the connector — whichever of source/destination has no VObject at all this call — is left exactly as prior had it, the same “leave whatever was there before untouched” convention _clippedArc()’s failure path already uses above, rather than being deleted: a caller that flips back and forth between one- and two-endpoint calls doesn’t lose track of ids it may still want.

Parameters:

  • label (VObject) – One end of the single line actually drawn (the end both lines of a full connector would otherwise pass through).

  • other (VObject) – The one present endpoint — whichever of source/destination isn’t None.

  • otherIsSource (bool) – True if other is standing in for source (so the terminators.source/labelNear slots, and the sourceLineID/ sourceTerminatorID/labelNearTerminatorID result fields, apply); False if it’s standing in for destination (labelFar/destination slots and destLineID/labelFarTerminatorID/destTerminatorID fields).

  • tagList (list) – Canvas tags, already coerced to a list by the caller.

  • lineOpts (dict) – The base {'fill': lineColor, **lineKwargs} dict the caller already built.

sn.view.graphics.connectors.drawSmoothConnector(source, label, destination, terminators=None, ids=None, *, lineColor='black', fillColor='', tags=None, **lineKwargs)¶

Draw source→label and label→destination as two lines that terminate at the edges of their respective VObjects and together trace ONE smooth quadratic-Bezier curve running from the center of source’s bounding box, through the center of label’s, to the center of destination’s.

The curve is a single quadratic Bezier [Cs, P1, Cd] chosen so it passes exactly through Cl (label’s center) at t=0.5 (see _labelControlPoint), then split at that point into two Bezier arcs — mathematically the same curve, so there’s no kink at the join even though it’s drawn as two line items. Each arc is then clipped to the exact portion between its two shapes’ boundaries (_clippedArc, via boundary-parameter bisection against VObject.containsPt() — the curved-path analogue of VRelation. findIntersection()’s straight-line bisection) and rendered as a Tk create_line() with exactly 3 points and smooth=True — Tk’s documented control-point quadratic-bezier behaviour for a 3-point smoothed line, so the rendered curve matches this function’s own math exactly.

Assumes source, label and destination don’t overlap each other and share the same canvas (source.canvas is used).

If source is destination (a self-loop – the same VObject on both ends), their centers are pushed a small distance apart first (see _selfLoopOffset()) so the source→label and label→destination arcs come out as two distinct, roughly parallel loops instead of retracing the exact same curve on top of each other.

source and/or destination may be None. If exactly one is None, only a single straight-line segment is drawn – from label to whichever of the two is actually present, complete with that segment’s own terminators – since a curve needs a third point to bend around; with only two points there’s nothing to smooth either way, so drawStraightConnector() behaves identically in this case. The OTHER side’s previous canvas items (if any) are left untouched, exactly as when a boundary clip fails elsewhere in this module – see _drawSingleSegment(). If both are None there’s nothing to connect to at all, so the call is a silent no-op: nothing is drawn or deleted, and ids (or an empty ConnectorIDs() if ids was also None) is returned unchanged.

Parameters:

  • source (VObject | None) – The VObject the first line starts from, or None if there is no source object.

  • label (VObject) – The VObject both lines connect through.

  • destination (VObject | None) – The VObject the second line ends at, or None if there is no destination object.

  • terminators (ConnectorTerminators | None) – The four terminator specs (source/labelNear/labelFar/ destination), or None for no terminators at all.

  • ids (ConnectorIDs | None) – A previous call’s ConnectorIDs, to update those exact items in place instead of creating new ones. None (the default) draws fresh items. Every colour/terminator/line option is re-applied from this call’s arguments regardless — nothing is assumed to carry over from whatever ids was drawn with.

  • lineColor (str) – Passed as create_line()’s “fill” (and terminators’ outline colour) unless overridden via lineKwargs.

  • fillColor (str) – Fill colour for “circle” terminators.

  • tags (Sequence[str] | None) – Canvas tags applied to every item this call touches.

  • lineKwargs – Extra options merged into both create_line() calls (width, dash, etc.).

Returns:

The ids of everything drawn, for passing back in on the next call (or deleting).

Return type:

ConnectorIDs

sn.view.graphics.connectors.drawStraightConnector(source, label, destination, terminators=None, ids=None, *, lineColor='black', fillColor='', tags=None, **lineKwargs)¶

Same signature and result shape as drawSmoothConnector() — a drop-in “fast” alternative that draws two straight lines (source-to-label, label-to-destination) instead of a smooth curve. Intended for contexts where the curve’s cost isn’t worth it, e.g. every frame of a drag/animation, with a swap to drawSmoothConnector() once things settle — hence the identical signature: calling code can hold either as a plain function pointer and not care which one it has.

Like drawSmoothConnector(), passing a previous call’s ConnectorIDs back in via ids updates those items in place (and works even if ids was last drawn by drawSmoothConnector() — the same items just get reshaped from a 3-point smoothed arc to a 2-point straight segment).

Also like drawSmoothConnector(), source is destination (a self-loop) is special-cased – see its docstring and _selfLoopOffset() – so the two segments end up offset and roughly parallel instead of drawn one on top of the other.

source and/or destination may be None, with exactly the same behaviour as drawSmoothConnector(): a single terminator-and-all straight segment from label to whichever one is present if only one is None (see _drawSingleSegment()), or a silent no-op returning ids (or a fresh, empty ConnectorIDs()) unchanged if both are.

  • fillColor (str)
