sn.model.clingoReasoner module¶

A Reasoner engine built on clingo (answer set programming).

The engine-neutral facts from Reasoner.facts() are rendered as ASP facts, the rule base in clingoReasoner.lp is applied, and the resulting atoms are mapped back onto the model’s GraphObjects. Every GraphObject is reified as a term o(N), which is what lets relation types take part in the isa hierarchy (and relations relate relations) while staying first-order.

_patternBody(pat, var, forRule=False)¶

The clingo body literals for pat. var maps each variable’s name to its clingo variable (variables with the same name are the same variable), and gets value variables (“?a”) added.

Variables range over data only (see GraphObject.isPatternElement()): over individuals, types, or both, by their kind (see GraphObject.variableKind(): eg: “?x”, “^T”, “!a”) – and over relation types if used as one, whatever their kind. A query’s variables also range over the objects rules create; a rule’s (forRule: a rule that creates objects) don’t – or it could go on creating objects forever.

_rulesProgram()¶

The rules (see reasoner.ruleOf()) – the model’s, its super-models’ and the base rules (see Reasoner.ruleObjects()) – as clingo rules, one per conclusion: fired(Rule,T,S,D) :- <antecedent>. for a relation, and rule_attr(Rule,X,Key,Value) :- <antecedent>. for an attribute. (The rule base takes these as holds/3 and attr/3.) The constraints (see reasoner.constraintOf()) likewise: violation0(Code,Severity,Subject,(Args,)) :- <pattern>. – for a requirement, requirement_holds(Req,(Vars,)) :- <condition>, <required>. and violation0(...) :- <condition>, not requirement_holds(Req,(Vars,)). over the condition’s variables. A rule or constraint with problems isn’t used: its problems are reported as violations. Call after rendering the facts (see _program()).

Return type:

str
