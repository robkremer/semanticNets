snplugins.XMLreader.reader module¶

Turn an XML file into a Semantic Nets model (see buildModel()), built on an ontology of its own: a second model, a super-model of the first, which has the types and the definitions – so there’s one place to change the type hierarchy, add rules, and so on. The model has the elements.

What each tag and attribute is – a node tag, a property, a group, a list holder, an annotation, a kind, a reference – is inferred from how they’re used throughout the file (see schema). Then:

  • Each node tag becomes a type (a node isa node), the first time it’s seen, with a look of its own (see TypeLooks), which its individuals inherit, and a tooltip listing its properties (see tooltip()).

  • Each of its elements becomes an individual of its tag’s type – or, if its tag has a kind field (see schema), of a subtype of the tag’s type named by its value (eg: <book kind=”novel”> is an individual of novel, which isa book), made the first time it’s seen. Subtypes look like their tag’s type, in a different shade.

  • Its fields – its XML attributes, and its property subelements (and those in its groups) – become its individual’s attributes, “property/<name>”, of the datatype their values are; its type has each (with no value), with a note saying where it’s from.

  • Its text (if it isn’t just white space) becomes its individual’s “text” attribute.

  • A nested node element’s individual is related to its containing element’s by a relation of type “has-<tag>” (eg: a book element’s has-chapter relations to its chapters); a list holder’s elements, by “has-<holder>” (eg: has-DeviceList, to each device). Each is a kind of xml-has-part (see HAS_PART), so the elements’ tree is there whatever the tags.

  • xml-part-of (see PART_OF) is the other way round: it’s defined (a definition in the ontology) as [?a -xml-part-of-> ?b] <-> [?b -xml-has-part-> ?a], so the reasoner concludes it.

  • A reference field (eg: DeviceID) also relates the individual to the one it refers to, by a relation named for the field: a kind of xml-refers-to (see REFERS_TO).

  • An individual is named by its name, title, label, id or key field, or its short text (see schema.Schema.nameOf()); otherwise by its tag and a number (eg: chapter1, chapter2, …).

Namespaces are dropped from tag and attribute names (eg: “{http://…}book” becomes “book”).

The ontology can be one made before, for the same file (eg: by reading it again, after changing the ontology: moving types about, adding rules, …), or for files of the same kind (one ontology, shared by their models): buildModel() builds on it, and adds only what’s missing – to it, or, if it can’t be changed (eg: it’s on the web: see canChange()), to the model (an attribute its types haven’t is then just in the elements). What’s in it is found by name:

  • a tag’s type, by the tag (any node type of that name: wherever it is in the type hierarchy);

  • a subtype, by its “type” or “kind” attribute’s value: one of that name that’s a kind of its tag’s type (at any depth: eg: under another subtype);

  • has-<tag>, has-<holder>, a reference’s field, HAS_PART, PART_OF and REFERS_TO, by name (relation types);

  • what the tags are, as far as it says (see hintsFrom()): a tag with a type there is a node tag, and one a type there has a property for is a property.

What isn’t found – something the XML has that the ontology doesn’t, or one renamed or deleted since – is made afresh, as for a new ontology, with a look of its own, and logged; so is an attribute of an element that its type doesn’t have (nor inherit). (A has-<tag> found whose range its tag’s type isn’t a kind of – eg: the type was renamed, and so made afresh – is left as it is, with a warning: the reasoner would find each element out of range.) If PART_OF isn’t there, it’s made with its definition; if it is, its definition is left as it is (or isn’t: one deleted stays deleted).

snplugins.XMLreader.reader.HAS_PART = 'xml-has-part'¶

The relation type every has-<tag> is a kind of: from an element to each element in it.

snplugins.XMLreader.reader.PART_OF = 'xml-part-of'¶

The relation type defined as the inverse of HAS_PART: from an element to the element it’s in.

snplugins.XMLreader.reader.REFERS_TO = 'xml-refers-to'¶

The relation type every reference’s is a kind of: from an element to one a field of it identifies (see schema).

snplugins.XMLreader.reader.SHAPES = ('Rectangle', 'RoundedRectangle', 'Oval', 'Hexagon', 'FileFolder', 'RightParallelogram', 'LeftParallelogram', 'TopPentagon', 'RightPentagon', 'LeftPentagon')¶

The shapes the types are given (see TypeLooks).

class snplugins.XMLreader.reader.TypeLooks(seed)¶

Bases: object

A look – fill and border colours, and shape – for each type, chosen at random, but the same each time for the same XML file. The fills’ hues are spread out (by the golden ratio), so types made one after another look different; their individuals inherit the look, so it shows which type each is. A subtype (see applyShade()) keeps its type’s hue and shape, in a shade of its own. Types already there (in an ontology made before: see reuse()) are counted as they come, so new ones look as they would have, had they been made with them.

snplugins.XMLreader.reader.buildModel(xmlPath, modelPath, ontology=None, extendOntology=True, found=None)¶

Make a model of the XML file xmlPath (as described in the module doc), as a new model file modelPath, and its ontology (beside it, unless ontology says where: see ontologyPath()): its super-model – or build on ontology, adding to it what’s missing (see the module doc), or, if it can’t be changed, putting that in the model. (Neither’s saved: call their save().)

Parameters:

  • xmlPath (str) – The XML file.

  • modelPath (str) – The model’s file: it mustn’t exist yet (nor the ontology’s, if one’s made).

  • ontology (Model | str | None) – An ontology made before (eg: for the same file, or one shared by files of the same kind, read from its file or URL), to build on; or the file to make one in; or None, to make one beside the model.

  • extendOntology (bool) – Whether what ontology is missing goes in it: if not – or if it’s write-locked (eg: it’s on the web: see Model._wasRead()) – it goes in the model (types, has-<tag>s, …), and an attribute its types haven’t is just in their elements. (See canChange().)

  • found (list[str] | None) – If given, what the tags were found to be (see schema.Schema.report()) is added to it.

Returns:

The model, and its ontology.

Return type:

tuple[Model, Model]

Raises:

xml.etree.ElementTree.ParseError – if the file isn’t well-formed XML.
